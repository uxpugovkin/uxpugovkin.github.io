Making broken records visible

JTBD №1

When attributes fail to sync and I only find out because someone reports lost access, I want to see empty attributes and stale sync times right in the user list, so I catch broken records before they turn into tickets

  • Designed a new table with columns to help admins spot users with issues
  • Designed import/export workflows for bulk attribute updates (very helpful, hard to measure)
  • Insisted on starting search when 1 character is entered (short-name case was missed)
  • Insisted on collapsing 5 search fields into one search bar (admins do not need to choose a field)
  • Insisted on highlighting stale sync dates for easy spotting

UX test revealed that users do not like “filled” or “empty” attributes because they are not an error or mistake. “Assigned” and “unassigned” are completely normal, and sometimes it happens.

Spotting the attribute that broke

JTBD №2

When a user can’t reach a resource their colleague can, I want to compare both sets of attributes, so I can spot the difference myself instead of reading raw files

  • Researched JSON diff methods and aligned with technical constraints
  • Prototyped and proposed a new workflow
  • Chose overlaps over split view (spots differences instantly, no eye scanning needed)

After UX test, added login names and labels for both JSONs to make it more obvious.

For an admin hunting the attribute that breaks a user’s access, the unified view keeps everything in one column, with both values of each changed attribute on a single line. The eye moves straight down the list and never jumps between columns to match rows. Identical lines appear only once, so the differences stand out and the admin reaches the broken attribute faster.

“It worked yesterday” — an investigation

JTBD №4

When a user loses access they had yesterday, I want to compare their attributes before and after in the ABAC UI, so I can see which one dropped without asking a developer to pull the data

  • Designed a brand new workflow
  • Reused JSON diff widget
  • Proposed two options
  • Insisted on keeping search and share buttons visible (do not hide features under hotkeys)

Option A — the user searches, filters, and pins two history snapshots using the bulk-operation table controls, then clicks the compare button. Option B — the user finds the snapshot with no issues and compares it with the current state in one click.

Option A was attractive because it seemed easy to enable every possible table component feature. Option B won the tradeoff, because it compares the current snapshot with a chosen one in a single click, without the cumbersome table UI and its four-plus user clicks.
